# 12 — DDJ-400 as the control surface for the XDJ-RX3 engine

Goal: plug a **Pioneer DDJ-400** into the Chromebit's USB-A port and use it to
drive the standalone rekordbox engine (`rbp`) running on the HDMI screen —
i.e. the Chromebit becomes a rekordbox "console" whose physical controls are a
DDJ-400 instead of the XDJ-RX3 front panel that `rbp` normally expects.

Status:

| Part | State |
|---|---|
| MIDI → engine control path (`bridge` → FIFO → `keyshim` → `sendKey`) | ✅ done, verified (self-test §6) |
| DDJ-400 MIDI mapping (transport, mixer, jog, tempo, pads, loops, Beat FX) | ✅ written from the official MIDI list, verified on hardware for transport/browse/pads/mixer |
| DDJ-400 **USB enumeration** on the Chromebit | ✅ works when connected **directly**; ❌ fails through the bus-powered hub (§7) |
| Full live mapping pass on hardware (pads per mode, Beat FX, jog feel) | 🔶 partially verified — see the handover doc `docs/14` |
| Audio through the DDJ-400 (master out + headphone cue) | 🔶 planned (§8) — not needed for now, audio goes to the TV |

## 1. Why a bridge is needed

Two facts shape the design:

* **`rbp` has no MIDI input at all.** It is the XDJ-RX3 application: it reads
  keycodes from Pioneer front-panel microcontrollers through its internal
  `IKeyManager::sendKey(keycode, op, ch, param, f, l)`. A DDJ-400 is a plain
  USB-MIDI class device, so nothing in the engine can see it.
* **`keyshim.so` already owns the injection path.** It is `LD_PRELOAD`ed into
  `rbp`, resolves the live `KeyManager` singleton and forwards records from
  `/tmp/rb-keys.fifo` (docs/09). Adding a second FIFO for *values* (faders, jog
  speed, knobs) extends it to a full control surface without touching `rbp`.

So the DDJ-400 is translated, not emulated:

```
DDJ-400 ──USB MIDI──▶ ddj400-bridge ──24B records──▶ /tmp/rb-ctrl.fifo
                       (host rootfs, musl)                    │
                                                              ▼
                    keyshim.so  ──▶  IKeyManager::sendKey(key, op, ch, param, f, l)
                    (LD_PRELOAD in the soft-float chroot)     │
                                                              ▼
                                                    rbp UI + audio engine
```

The bridge runs on the **host** rootfs (hard-float postmarketOS, `gcc`
available), not in the soft-float chroot: it only needs `/dev/snd/midiC*D*` and
the shared `/tmp`. It deliberately has **no libasound dependency** — it reads
the ALSA rawmidi character device directly and parses MIDI itself, so it builds
with the device's own compiler in one second and never needs cross-building.

## 2. The control FIFO protocol

`/tmp/rb-ctrl.fifo` carries fixed **24-byte** records (a FIFO has no framing, so
the record size must be constant; this is why a second FIFO is used instead of
extending the 12-byte key record):

```c
struct ctrl_ev {
    int32_t key;    /* rbp keycode, e.g. 0x4101 = PLAY               */
    int32_t ch;     /* deck/mixer channel: 1 = deck 1, 2 = deck 2    */
    int32_t op;     /* 0 press, 2 release, 4 rotate, 5 absolute      */
    int32_t param;  /* op4/5: 10-bit value 0..1023, or ±delta        */
    float   f;      /* op4: speed (rev/s)   op5: normalised value    */
    int32_t l;      /* spare/position (jog virtual position)         */
};
```

`op` semantics are the ones live-verified for the Prime GO
(`PrimeBox/scripts/shims/knobshim2.c`):

| op | meaning | payload |
|---|---|---|
| 0 / 2 | press / release | — |
| 4 `OP_ROTATE` | **absolute** for faders/EQ/trim/crossfader/cue knobs (10-bit) **and** relative for the browse knob (±1) | `param`, `f` = normalised |
| 5 `OP_VALUE` | Sound Color FX knob, Beat FX depth, tempo slider | `param` = 10-bit, `f` = normalised (tempo: −1…+1) |

While a controller is active, `keyshim` **stops re-applying the synthetic mixer
defaults** (they exist to unmute an engine with no hardware; left running they
would snap the physical faders back every 10 s).

Notes and caveats:

* The DDJ-400 has no BACK/SOURCE/MENU/VIEW/TAG buttons. MENU is still reached
  via **SHIFT+LOAD 2**, and SOURCE (device picker: USB1/USB2/PC) via
  **SHIFT+LOAD 1**. Opening the library from the plain rotary push went
  through three iterations, all confirmed live:
  - `K_SOURCE`: opens the SOURCE/device-picker screen, not the file list --
    forces a 2-step dance (push -> SOURCE screen -> push again -> file list)
    on *every* open, since the picker doesn't remember a prior USB choice.
  - Plain `K_SELECTOR` (skipping `K_SOURCE` entirely): does **nothing** from
    the closed/deck view.
  - `K_BACK` (the same key SHIFT+push already used for "back"): goes
    straight to the file list in one press. This is what's deployed now.
  The bridge tracks browser-open state itself (`browser_open`): the 1st push
  sends `K_BACK`, subsequent pushes send `K_SELECTOR` (select/enter)
  instead. Only LOAD-ing a track resets it back to "closed" (there is no
  reliable signal for "backed all the way out without loading anything";
  see below). `browser_open` is only ever set from `handle_note()`'s
  `handle_interface_toggle_note()` (SHIFT+push) and from the plain-push and
  LOAD blocks in `led_handle_input()` -- it must **not** also be touched by
  `led_handle_input()`'s own note-0x42 case, since that runs *before*
  `handle_interface_toggle_note()` reads it on release to choose BACK vs
  SOURCE; resetting it there made every SHIFT+push look like "closed" and
  silently broke BACK while actually browsing (regression, fixed).
* **SHIFT is note 0x3f on each deck's own MIDI channel** (each deck has its
  own physical SHIFT key), a pure hardware-level modifier: holding it changes
  the note number of whatever other button is pressed on the same channel
  (e.g. PLAY 0x0b -> 0x47 CENSOR/REVERSE), confirmed via raw `amidi -d`
  capture. It carries no meaning by itself and `led_handle_input()` ignores
  it. An earlier version of this file wrongly mapped it to `K_LOAD`, which
  silently reloaded the deck every time SHIFT was held for any other combo
  (e.g. SHIFT+PLAY, SHIFT+SYNC) — fixed. The real LOAD buttons are note
  0x46/0x47 on `MC_MIXER`, also confirmed via raw capture. It **is** tracked
  in `shift_held[deck]` though, since MC_MIXER controls on a different
  channel (e.g. MASTER CUE) have no other way to know SHIFT is down —
  holding SHIFT on either deck sets `shift_held[]`, the hardware doesn't
  need to renumber MASTER CUE's own note for that to work in software.
* **SEARCH** is SHIFT+MASTER CUE, by user request. Confirmed live via raw
  MIDI capture: SHIFT+MASTER CUE sends a **different note, 0x78** on
  `MC_MIXER` (not 0x63 with a separately-detected SHIFT flag) -- same
  pattern as PLAY(0x0b)->CENSOR(0x47) and LOAD(0x46)->SOURCE(0x68). An
  earlier version tried detecting it via `shift_held[]` on note 0x63, which
  never fired since the hardware never actually sends 0x63 while shifted.
  It's a toggle:
  - Press once: sends `K_SEARCH 0x0205` (opens the on-screen keyboard) and
    starts blinking the MASTER CUE LED at 1Hz (`search_led_tick()`, called
    from the main poll loop like the other LED tickers).
  - Press again: sends `K_BACK` (best-effort close) and stops the blink,
    restoring the LED to the normal `led_master_cue` state.
  - There's no real feedback from the engine about whether the keyboard is
    actually open, so `search_cancel(fd)` is also called (best-effort) from
    every other navigation action that plausibly means "I left search":
    LOAD-ing a track, a plain BROWSE push, and SHIFT+push resolving to BACK
    (i.e. while already browsing). If the keyboard is closed some other way
    (e.g. directly on the touchscreen) none of these fire and the LED can be
    left blinking -- press SHIFT+MASTER CUE again to force it off.
* **Crossfader curve** is SHIFT+FX CH1/CH2/MASTER (the Beat FX channel-select
  buttons), by user request, each selecting a different, specific curve
  (confirmed live by injecting raw `ctrl_ev` records into the FIFO and
  reading back what changed on screen): `K_FADERCURVE` op5 param 0 = THRU,
  1 = normal fader curve, 2 = sharp/cut curve, 3 = a 4th distinct curve
  (visibly different from THRU). Only 1/2/3 are wired to CH1/CH2/MASTER per
  user choice; param 0 (THRU) is valid but unused here. Unlike MASTER CUE,
  raw capture confirmed SHIFT does **not** renumber these buttons' notes (the
  hardware always sends 0x10/0x11/0x14, plus the auto-OFF of whichever was
  previously selected — `handle_fxch()`'s existing behavior), so
  `shift_held[]` is the only way to detect the combo here.
* Pads are mode-implicit: the DDJ-400 sends `mode*16 + (pad-1)` according to
  the selected pad mode (confirmed live via raw MIDI capture that the note
  ranges match the header comment in `pad_rx3_bank()`/`handle_pad()`: modes
  cycle physically in the order HOT CUE → BEAT LOOP → BEAT JUMP → SAMPLER →
  KEYBOARD → PAD FX1 → PAD FX2 → KEY SHIFT, but the *note value* is what the
  bridge keys off, not cycle order, so this doesn't matter for correctness).
  The bridge switches the engine's pad bank before the first pad of a new
  mode. Direct RX3 equivalents: HOT CUE, BEAT JUMP, and **BEAT LOOP**
  (fixed — it used to be wrongly swapped with SAMPLER's fallback, sending
  BEAT LOOP's own pads to the SLIP LOOP bank while SAMPLER, which has no
  real RX3 equivalent, occupied the native BEAT LOOP bank instead). Modes
  without an equivalent (PAD FX1/2, SAMPLER, KEYBOARD, KEY SHIFT) fall back
  to SLIP LOOP or BEAT JUMP or HOT CUE, best-effort, per user choice; PAD FX2
  is additionally special-cased to drive the STEMS DRUMS/VOCAL/INST toggles
  instead of any RX3 pad bank (see `handle_pad()`, mode 5). **Mode 7 (KEY
  SHIFT)** -- reached via SHIFT+SAMPLER, confirmed live: the mode-select
  announce note is 0x6F (not 0x22, SAMPLER's own), and pads then use range
  0x70-0x77 -- has no RX3 equivalent either and is wired to the same STEMS
  page as a second entry point, by user request.
* Each pad-mode button also sends its own "announce" note the instant it's
  pressed (before any pad is touched), separate from the pad-press bank
  switch above -- see the `notemap[]` rows above. This table had a bug:
  0x1E ("beat loop") was never actually sent by the hardware (the real BEAT
  LOOP button sends 0x6D, confirmed live), so pressing it announced nothing,
  while SAMPLER's real note (0x22) was wired to `K_ALOOP` -- beat loop's own
  announce key -- instead of `K_SLIPLOOP`. Net effect: pressing SAMPLER
  wrongly flashed a beat-loop reaction, and BEAT LOOP's own button looked
  inert until a pad was actually pressed. Fixed to match the pad-bank
  fallback (SAMPLER -> SLIP LOOP, BEAT LOOP -> its own native bank).
* **Double-click pad-mode layers** (by user request, confirmed live): the
  RX3 engine has **8** native pad banks, not 4 -- `keyshim.c`'s
  `rx3_select_pad_bank(deck, target)` already supported this (target 0-7),
  in 4 families of 2 (`target % 4`): pressing the *same* mode-announce key
  twice in a row (0x1B/0x6D/0x20/0x22 above, which double as
  `RX3_NATIVE_PAD_SELECTOR + family`) toggles natively between the two
  layers of a family -- HOT CUE↔**GATE CUE**, BEAT LOOP↔**BEAT LOOP 2**,
  BEAT JUMP↔**BEAT JUMP 2**, SLIP LOOP↔**RELEASE FX**. This already worked
  with no changes needed. The bug was in `keyshim.c`'s
  `rx3_handle_tagged_pad()`: every pad press also carries a
  `0x5040 | bank` tag (see `handle_pad()`) that *unconditionally* forced the
  engine back to the bridge's hardcoded layer-1 bank (0-3) -- since that's
  the same `RX3_NATIVE_PAD_SELECTOR` toggle key, forcing it while already on
  layer 2 silently flipped back to layer 1 every time a pad was touched.
  Fixed: `rx3_handle_tagged_pad()` now only forces a switch on a genuine
  cross-*family* mismatch (`actual % 4 != bank % 4`); if already in the
  requested family it trusts whichever layer (1 or 2) is actually active.
* The DDJ-400 has no MIC or booth controls, and the RX3 "tag list"/"info" keys
  are unused.
* The FILTER knob maps onto the RX3 **Sound Color FX** knob; run
  `ddj400-bridge -F` once (or `-F` at startup) to select the FILTER colour-FX
  type, otherwise whatever type is selected applies.
* Jog speed needs calibration: `-J <pulses-per-rev>` (default 1800). Spin the
  jog exactly one turn with `-v` and read the accumulated delta in the log.
* **Mixer control sync on startup (pickup + persistence, 2026-09-27).** The
  DDJ-400's pots/faders are plain absolute MIDI controls: they only transmit
  on physical movement, so nothing (bridge or engine) can query a control's
  actual position on boot -- a hardware/firmware limitation of the
  controller itself, confirmed against the official MIDI message list, not
  something worth chasing further. Without a fix, the engine starts at
  `keyshim`'s hardcoded `mixer_defaults()` (fader up, trim/EQ/crossfader
  centred) regardless of where the physical control actually is, so the
  first touch after boot used to jump the mix straight to the physical
  value. Two mechanisms now cover this, for all 18 continuous controls
  (the 16 `cc14[]` entries plus FILTER ch1/ch2, which is a plain 7-bit CC
  handled separately in `handle_cc()`):
  - **Soft takeover ("pickup")**: each control tracks a `target10` (the
    value the engine was primed to) and stays inert -- physical movement is
    read but not forwarded -- until the incoming value actually crosses
    that target, exactly like Mixxx's `softTakeover` or Traktor/Serato's
    equivalent. Once crossed it engages and follows 1:1 from then on. This
    is the safety net: it's what actually prevents the jump, independent of
    where `target10` came from.
  - **Persistence**: every value actually forwarded is saved to
    `rx3-mixer-state.bin` (sibling of the control FIFO -- real disk under
    `work/runtime/rx3/tmp`, *not* `/tmp` tmpfs, so it survives a reboot).
    On the next boot it's loaded and used as `target10` instead of the
    hardcoded default. Since the controller is normally untouched across a
    quick service/system restart, this makes the pickup threshold match the
    real physical position almost exactly, so takeover engages on the very
    first, imperceptible nudge instead of requiring the control to be
    racked all the way to the old hardcoded default first. If the file is
    missing or corrupt (first-ever boot) it silently falls back to the
    hardcoded defaults -- pickup alone still prevents the jump either way.
  Live-validated 2026-09-27: restarted the service after moving several
  controls, log showed `loaded 18 persisted mixer control(s)`, and a
  control with a genuinely non-default persisted value (FILTER ch2 = 516,
  not the hardcoded 512) was confirmed used as the new pickup target.
* **Sound Color FX type select (2026-09-27).** The FILTER knob only
  controls the *value* of whichever Color FX type is currently selected;
  the DDJ-400 has no physical selector for the *type* itself (real Pioneer
  mixers have a 3-position switch next to the knob for this). By user
  request, **SHIFT+BEAT LOOP** (note `0x1E`, confirmed live -- this is
  officially "PAD FX mode 1" per the Pioneer MIDI Message List v1.00, *7)
  repurposes the performance pads as a type selector: pad 1 → type 1
  (FILTER), pad 2 → type 2 (NOISE), pads 3-5 → types 3-5 (unnamed but
  confirmed functional live), pad 6 → type 6 (CRUSH). Types 0 and 7+ are
  confirmed no-ops (tested live with slow full-range knob sweeps, not just
  a quick check). Selection is per deck. Implementation: `handle_pad()`
  intercepts `mode == 1` before it would otherwise fall through to
  `pad_rx3_bank()`'s old (dead, redundant with SAMPLER) SLIP LOOP fallback,
  and sends a new keyshim-only pseudo-key (`K_COLOR_TYPE 0x50a7`, not a
  real rbp keycode) over the control FIFO; `keyshim.c`'s
  `rx3_native_color_fx_select(deck, type)` (generalised from the old
  hardcoded-`type=1`-only `rx3_native_filter_select()`) calls the same
  native function `mixer_defaults()` already used at startup, just with a
  live-discovered `type` instead of the hardcoded `1`.
  - **Known limitation: the pad LEDs don't track the selection.** Only pad
    1's LED (the type-1/FILTER default lit at connect) is ever visibly lit;
    selecting any other pad changes the *effect* correctly (audible, and
    confirmed via the FIFO/keyshim logs every time) but that pad's LED
    never lights, even momentarily. This is **not** a known-cause bug --
    eleven distinct explanations were tested live and ruled out with hard
    evidence, including: other LED writers colliding (disabled VU/hotcue
    telemetry/STEMS entirely, no change), timing after entering the mode
    (tested pressing a pad immediately after SHIFT+BEAT LOOP), the page
    only redrawing once on entry (re-entering the mode doesn't refresh
    it), a silently-dropped `EAGAIN` write with no retry (added retry +
    logging; the log never shows a drop -- every write is accepted by the
    kernel), synchronous-with-read vs. deferred-to-next-tick writes, a
    second write fd on top of the shared `O_RDWR` handle (`EBUSY`), fully
    separate `O_RDONLY` + `O_WRONLY` fds (opens fine, no `EBUSY`, still no
    LED), a 100ms read-silent window around the write, and blocking vs.
    non-blocking writes. The protocol itself was cross-checked against the
    official *DDJ-400 List of MIDI messages v1.00* (downloaded and read
    directly): PAD FX mode 1's pad LEDs are documented as
    `← Same as MIDI-IN`, i.e. plain Note On/Off, with **no footnote
    distinguishing them from Hot Cue's** (which works perfectly). Manually
    driving every note we use (`amidi -S`, single messages, combined in one
    session, back-to-back with no delay) lights and unlights every pad
    correctly and reliably, every time, in isolation -- so this is
    specifically about our long-lived bridge process's connection to the
    device, not the wiring, the protocol, or the hardware in general.
    Further diagnosis would need a USB protocol analyzer (e.g. Wireshark +
    usbmon) to see what actually changes on the wire between the two
    cases; out of scope for now. The feature ships without the LED
    confirmation -- selection is fully functional by ear.

## 5. Build & deploy

```sh
WORKSTATION$ ./scripts/rb/build-shims.sh keyshim.so     # soft-float, adds the ctrl FIFO
WORKSTATION$ PASS=<password> HOST=root@chromebit.local \
             ./scripts/rb/deploy-ddj400.sh              # builds the bridge on the device
CHROMEBIT#   sh /home/user/start-rb.sh                  # player + bridge
```

The deploy script compiles `ddj400-bridge` **on the Chromebit** (it has gcc and
no dependencies), installs it as `/usr/local/bin/ddj400-bridge`, installs the
new `keyshim.so` into the chroot, and enables a `ddj400-bridge.service` so the
bridge also comes up on boot.

`keyshim.so` with ctrl-FIFO support: md5 `c09ff18b31722db6f8e4875323c795f7`
(still only `GLIBC_2.4`).

## 7. USB: direct connection works — the hub was the problem

**Resolved.** The controller enumerates and works when plugged **directly**
into the Chromebit:

```
usb 1-1: New USB device found, idVendor=2b73, idProduct=0026
usb 1-1: Product: DDJ-400   Manufacturer: Pioneer DJ Corporation
card 1 [DDJ400]: USB-Audio - DDJ-400 at usb-ff580000.usb-1, high speed
/dev/snd/midiC1D0            -> the bridge attaches automatically
```

Through the bus-powered USB2.1 hub it never got past address assignment:

```
usb 1-1.2: new high-speed USB device number 21 using dwc2
usb 1-1.2: device not accepting address 21, error -71
usb 1-1.2: device descriptor read/8, error -71      (107 attempts in one session)
```

Facts established on the device:

* the kernel side was never the problem: `CONFIG_SND_USB_AUDIO=m`,
  `snd-usb-audio` + `snd-usbmidi-lib` load, `alsa-utils` (`amidi`, `aconnect`)
  and `snd-virmidi` are present, and `usbcore.old_scheme_first=1` is already in
  the cmdline;
* the hub reports `bmAttributes=0xe0` (claims self-powered) but has **no working
  per-port power switching**, and its PSU was not connected — a bus-powered hub
  cannot feed the DDJ-400's up-to-500 mA alongside the stick;
* `error -71` at descriptor/address stage is the classic signature of
  power/signal integrity, not a driver bug.

**Consequence for the setup:** the Chromebit has exactly one USB-A port, so
running controller **and** stick **and** keyboard at once requires a **powered**
hub (its own 5 V PSU) — verified fix: connect the DDJ-400 directly.  Everything
else in this document (bridge, mapping, FIFO protocol) is unaffected.

Status of the pieces when working through a hub, for reference:

```sh
CHROMEBIT# cat /proc/asound/cards        # -> a "DDJ-400" card
CHROMEBIT# ls /dev/snd/midiC*D*          # -> its raw MIDI node
CHROMEBIT# sh /home/user/ddj400-start.sh status
```

## 8. Phase 2 — audio through the DDJ-400 (headphone cue)

The DDJ-400 is a class-compliant USB audio interface: **main out on channels
1–2, headphones on 3–4** (the Mixxx manual configures exactly that). The RX3
engine `rbp` opens three stereo devices (master / headphone / booth), which
`audioshim` currently folds into the single stereo HDMI PCM (`hw:0,0`,
docs/08).

Because `audioshim` already distinguishes the master handle from the
headphone/cue handle, the DDJ-400 can be driven as a 4-channel device:

| rbp device | DDJ-400 PCM channels |
|---|---|
| master (`cs4344audiorev8,0`) | 1–2 → master out (RCA) |
| headphone/cue (`…,1`) | 3–4 → headphone jack |
| booth (`…,2`) | dropped |

That would give real headphone cueing with the DDJ-400's CUE buttons and
`HEADPHONES MIXING`/`LEVEL` knobs (already mapped to `K_HPMIX`/`K_HPLEVEL`).
Work items: open `hw:CARD=DDJ400` (4 ch, S24_LE/44100), keep HDMI as a fallback
when the controller is absent, and confirm the RX3 headphone mix is actually
produced by the engine once PFL is enabled.
